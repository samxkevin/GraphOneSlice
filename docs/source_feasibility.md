## Notes

- `usable` means the endpoint was accessible, parsed, and supplied the required fields for the implemented bounded adapter.
- `partial` means the source showed useful reachability or inventory evidence but was not accepted for ingestion without a stricter production adapter/filter.
- `unusable` means the source was not accessible or parseable enough in this environment to support ingestion.
- Several public web/RSS/API candidates failed at TLS/network connection setup in this environment. Those failures are retained in `data/validation_report.json` and `data/source_feasibility.json`.
- Product records are accepted only from the GitHub-hosted AI Tools List JSON directory sample when handle, website, description, valid URL, explicit AI description evidence, and product/service/platform semantics are present. Provider/company remains `null` because the source does not reliably supply it.
- The product adapter skips observed non-product blurbs such as guides and model-family/company descriptions, and deduplicates root `www` URL variants during discovery.
- Models.dev direct API access still fails from this environment, but the same open-source catalog is live-verified through GitHub REST contents. The Models.dev GitHub adapter adds bounded model records with source-supplied modality/capability metadata and leaves license `null` because the catalog does not provide per-model license fields.
- ROS Robots Catalog records are accepted only from robots.ros.org source posts that identify actual robot systems/components with title, description/introduction/body evidence, and catalog or website/wiki URLs. Software-support blurbs are rejected.
- ROS Robots front-matter dates are preserved as catalog post dates, not robot launch dates.
- GitHub Releases Announcements records are accepted only as News when a release has a valid canonical URL, a parseable `published_at`, a title, and a non-empty release-note body, and only from the curated AI repository allowlist. Draft and prerelease releases are rejected.
- GitHub release `published_at` is the genuine publication timestamp for the announcement; it is never substituted with crawl, retrieval, commit, or page-modification time. `timestamp_semantics` is recorded explicitly, and `fetched_at` remains a separate provenance field.
- `News → published_by → Company` relationships are emitted only when the release repository owner is a GitHub Organization that already resolves to an ingested company entity. OpenAI and Anthropic news records retain publisher metadata but no company relationship because their GitHub orgs supply no company description.
- Hacker News Algolia, GDELT, Himalayas, and Models.dev direct API probes remain recorded as unavailable through their direct endpoints. They are not accepted unless another reachable source path supplies the required fields.
- One-time reachability probes during the News milestone additionally confirmed that Hacker News Firebase API, Hacker News Algolia, news.ycombinator.com, Reddit JSON/API, Lobsters, Wikipedia API, GitHub Blog changelog RSS, RSSHub, raw.githubusercontent.com, and arXiv all fail at TLS connection setup in this environment. Only `api.github.com`, `pypi.org`, and `registry.npmjs.org` returned parseable JSON.
- NPM search package results are accepted only as package/tool records after explicit AI relevance checks and package-specific registry verification; they are not treated as product records.
- PyVideo Catalog records are accepted only as Videos when the source JSON supplies a title, a canonical YouTube URL, a parseable `recorded` date, a non-empty description, and AI relevance evidence from the title/description. Records are accepted only from the curated AI-relevant conference allowlist.
- PyVideo `recorded` is the source-documented date the talk was recorded — a recording date, not a publication/upload timestamp (PyVideo schema: "ISO 8601 Date on which video was recorded"). It is preserved as `video.recorded_at` with `timestamp_semantics = pyvideo_recorded_date` and is never substituted with crawl/retrieval time. PyVideo does not supply a YouTube channel name, so the publisher is recorded as the conference/event, not a fabricated channel identity.
- Videos produce no relationships: the source attributes talks to conferences (no company/developer entity exists for them), and no speculative `published_by`/`runs` edges are manufactured.
- AI Device Catalog records are accepted only from the source's "Available now" and "Boards with other AI/ML Accelerators" sections; "Available later" (announced-only) and "MCUs only" (bare chips) sections are excluded, and two boards sharing one generic catalog URL are deduplicated.
- Device manufacturer is derived only from the board name via a controlled, source-derived token map and recorded with `manufacturer_evidence`; it is `null` when the source does not name a manufacturer.
- The AI Device Catalog (boards) produces no `Device → runs → Model` edges: it documents framework support (TensorFlow/PyTorch), not specific supported model IDs.
- The Hailo Model Zoo supplies the `Device → runs → Model` evidence the boards catalog cannot: each model YAML declares `info.supported_hw_arch` naming the Hailo accelerators that run it. A `runs` edge is created only when a model's own YAML lists the device; the edge records the observed field, observed arch list, the model YAML blob URL, and the reason. Models without `supported_hw_arch` (six legacy face/person models) are excluded. No edge is inferred from framework/CUDA generality or popularity.
- Jobs candidates investigated this milestone: `SimplifyJobs/Summer2027-Internships` (reachable, parseable, 14,764 listing objects) and its sibling `SimplifyJobs/New-Grad-Positions` (reachable, 19,034 listing objects with the same schema). Both carry `company_name`, `title`, a per-listing application `url`, `locations`, `terms`, and `sponsorship`, but their `date_posted` is documented as "Unix timestamp when added" — the moment a listing was added to the list by Simplify's hourly scraper or a contributor, not the employer's posting time, and the contribution form does not collect a posting date. Because no genuine `posted_at`/`created_at` evidence exists, neither is accepted as a Jobs source, and no job records were fabricated.
- Personal candidate investigated this milestone: `elyase/awesome-personal-ai-assistants` is a curated Markdown "awesome" list of open-source, self-hosted assistant frameworks/tools (each entry a GitHub repository link with a one-line description and a language badge). It supplies no structured entity identity records and no personal-assistant product identities, so it fails the personal-AI-assistant identity gate and no personal records were fabricated.
- Live-source drift note: the NPM search tool source (`registry.npmjs.org` search endpoint) returns a time-varying result ordering; between pipeline runs the package `am-i-vibing` fell out of the bounded `keywords:llm` top-N sample (the package itself remains published at v0.5.0). This is a nondeterministic live-source observation, not a regression; the executed run's counts are authoritative and are recorded as-is.
- Candidates investigated and rejected this milestone: (1) a structured AI-companies catalog — GitHub repository search for "ai companies json/dataset" returns spam, course projects, and tooling, not a clean structured company dataset with canonical websites; (2) the MCP servers catalog (`modelcontextprotocol/servers`) — seven reference implementations plus SDK links, not a structured server catalog, and the real registry is a non-GitHub host unreachable from this environment; (3) Qualcomm AI Hub devices — `devices_and_chipsets.yaml` is authoritative (35 chipsets, 52 devices) but supplies no per-chipset canonical URL, so device records would carry weak/shared URLs and were deferred; and (4) Qualcomm AI Hub model→device compatibility — the per-model manifests declare no supported-device list, so no `Device → runs → Model` edges can be evidenced and none are fabricated.
- Qualcomm AI Hub Models was selected: it is a distinct authoritative catalog (new vendor), supplies license + license URL + domain + use_case + research paper per model, and yields 34 high-quality model records via a deterministic stride sample of the 236 published manifests.
- Hailo device identity is source-derived: the official README names Hailo-15H/15L/10H and documents each under `docs/public_models/<DEVICE>/`; `device.manufacturer = Hailo` (repository owner), `device.device_class = ai-accelerator`, and `device.canonical_url` is the device's own documentation directory in the source (the `hailo.ai` product pages are unreachable from this environment, so no unverified product URL is fabricated).
- Compatibility-source investigation (Device → Model): `airockchip/rknn_model_zoo` (RKNN examples lack a single clean per-model hardware field at the probed paths), `qualcomm/ai-hub-models` (device identity is rich via `devices_and_chipsets.yaml`, but per-model device support is expressed through `perf.yaml` benchmark scorecards rather than an explicit supported-device list), and `NVIDIA-AI-IOT/jetson_benchmarks` (benchmark CSVs, not a compatibility catalog) were probed and not selected over the Hailo model zoo's explicit `supported_hw_arch` declarations.
